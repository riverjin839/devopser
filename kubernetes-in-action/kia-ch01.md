## 1. 개요

- Kubernetes = 그리스어 "조타수(helmsman)". 방향은 선장(사람)이 정하고 조타는 K8s 가 맡음
- 정체 한 줄 : 컨테이너로 도는 대규모 앱의 배포·관리를 자동화하는 시스템
- 핵심은 API 하나 + 비교적 단순한 컨트롤러 묶음

<!-- diagram: kia-ch01-01-declarative.html -->

**원하는 상태를 적어 두면, K8s 가 현재 상태를 계속 그쪽으로 맞춤**

## 2. 개념 정리

### 2-1. K8s 가 해 주는 네 가지

| 항목 | 내용 |
|---|---|
| 인프라 추상화 | 노드·네트워크를 앱에서 숨김. 앱은 "클러스터" 하나만 봄 |
| 배포 표준화 | 같은 매니페스트로 온프렘·클라우드 어디든 배포 |
| 선언적 배포 | 구성 요소를 기술 → K8s 가 실행. 기술을 바꾸면 실행 상태도 따라 바뀜 |
| 일상 관리 인수 | 앱 죽으면 재시작, 노드 죽으면 다른 노드로 옮김 |

### 2-2. 프로젝트 배경

- Google 의 Borg → Omega 경험을 바탕으로 2014 년 오픈소스로 공개
- 2014 년에 이미 주당 20억 컨테이너 기동 수준이었다고 함
- 지금은 CNCF(Linux Foundation 산하) 생태계의 중심. OpenShift, Rancher 같은 상용 배포판도 여기서 파생

### 2-3. 왜 이렇게 퍼졌나

| 변화 | K8s 가 준 것 |
|---|---|
| 모놀리스 → 마이크로서비스 | 수십~수백 개 서비스 관리 자동화. 의존성 충돌은 컨테이너가, 개수 폭증은 K8s 가 해결 |
| Dev 와 Ops 의 벽 | 개발자는 서버 세부 몰라도 배포 가능 |
| 클라우드 종속 | 표준 API 로 클라우드 간 이동이 쉬워짐 |

### 2-4. 클러스터용 운영체제

- OS 가 프로세스를 CPU 에 스케줄링하듯, K8s 는 앱을 노드에 스케줄링함
- 앱이 직접 구현하던 기능을 K8s 가 대신 제공

| 기능 | 의미 |
|---|---|
| 서비스 디스커버리(Service discovery) | 다른 앱을 이름으로 찾음 |
| 수평 확장(Horizontal scaling) | 부하에 맞춰 복제본 수 조절 |
| 로드밸런싱(Load-balancing) | 복제본 전체에 트래픽 분산 |
| 자가 치유(Self-healing) | 실패한 앱 재시작, 죽은 노드의 앱을 건강한 노드로 이동 |
| 리더 선출(Leader election) | 여러 인스턴스 중 활성 하나를 정함 |

- 모든 워커 노드가 하나의 배포 공간처럼 보임
- 단, 앱 하나가 여러 노드에 쪼개져 도는 건 아님. 앱은 노드 하나에 들어갈 크기여야 함

### 2-5. K8s 를 쓰면 좋은 점

- 셀프서비스 배포 : 개발자가 노드 사정 몰라도 직접 배포. 배치는 스케줄러가 자원 요구량 보고 결정
- 비용 절감 : 앱을 아무 노드로나 옮길 수 있음 → 빽빽하게 채워 활용률 상승
- 부하 자동 대응 : 메트릭 보고 인스턴스 수 조절. 클라우드면 노드 자체도 늘림
- 장애 자동 복구 : 노드 100대, 노드당 MTBF 100일이면 하루 한 대꼴로 고장. 여유 자원만 있으면 새벽에 깰 필요 없음
- 개발 단순화 : 디스커버리·설정·리더 선출을 앱에서 빼냄. 필요하면 앱이 K8s API 를 직접 조회

## 3. 클러스터 구조

<!-- diagram: kia-ch01-02-architecture.html -->

### 3-1. 두 개의 플레인

- 컨트롤 플레인(Control Plane) = 두뇌. 클러스터 상태를 보관·제어
- 워크로드 플레인(Workload Plane) = 앱이 실제로 도는 워커 노드들
- 데이터 플레인이라고도 부르지만, 데이터가 아니라 앱이 올라가는 "면" 이라는 뜻
- 운영 HA 는 컨트롤 플레인 노드 최소 3대

### 3-2. 컴포넌트 역할

| 위치 | 컴포넌트 | 역할 |
|---|---|---|
| 컨트롤 플레인 | API Server | RESTful API 제공. 자체는 stateless |
| 컨트롤 플레인 | etcd | 오브젝트 저장소. API Server 만 직접 접근 |
| 컨트롤 플레인 | Scheduler | 앱 인스턴스마다 노드 결정 |
| 컨트롤 플레인 | Controllers | 오브젝트를 실체로 만듦. 대부분 다른 오브젝트를 생성 |
| 워커 노드 | Kubelet | 노드 에이전트. 앱 실행·상태 보고 |
| 워커 노드 | Container Runtime | Kubelet 지시대로 컨테이너 실행 |
| 워커 노드 | kube-proxy | 서비스 트래픽 로드밸런싱 |
| 애드온 | DNS, 네트워크 플러그인, 로깅 등 | 대부분 클러스터에 기본으로 깔림 |

> 주의 : 책은 런타임 예로 Docker 를 듦. Kubernetes 1.24 부터 dockershim 이 빠졌으므로 실제로는 containerd·CRI-O 같은 CRI 런타임을 씀

### 3-3. 앱이 실행되는 과정

<!-- diagram: kia-ch01-03-deploy-flow.html -->

1. kubectl 이 매니페스트를 오브젝트 단위로 쪼개 API 에 POST·PUT → API Server 가 검증 후 etcd 에 저장
2. 해당 타입을 맡은 컨트롤러가 통지를 받고 인스턴스 오브젝트(복제본 수만큼) 생성
3. 스케줄러가 각 인스턴스에 노드 배정. 스케줄러도 특수한 컨트롤러임
4. 배정된 노드의 Kubelet 이 런타임으로 컨테이너 실행
5. 인스턴스가 연결 받을 준비가 되면 kube-proxy 가 단일 IP 로드밸런서 구성
6. Kubelet 은 종료된 앱을 재시작하고 상태를 보고. 컨트롤러는 노드 장애 시 앱을 옮김

- 공통 패턴 : 모든 컴포넌트가 API 를 watch → 자기 일만 함 → 결과를 다시 API 에 씀
- 컴포넌트끼리 직접 대화하지 않음. API Server 가 유일한 허브

## 4. 조직에 도입할 때

<!-- diagram: kia-ch01-04-adoption.html -->

| 선택 | 옵션 | 장점 | 단점 | 언제 쓰나 |
|---|---|---|---|---|
| 어디서 | 온프렘 | 규제 대응, 임대료 없음 | 확장이 느림 | 규제상 사내 필수 |
| 어디서 | 클라우드 | 노드 증감 자유 | 사용료 | 사내 인프라 없음 |
| 어디서 | 하이브리드 | 평시 온프렘, 피크만 클라우드 | 구성 복잡 | 연 몇 번 피크 |
| 누가 | 직접 관리 | 완전한 통제 | 내부 동작을 깊이 알아야 함 | 경험 있는 팀 |
| 누가 | 매니지드(KaaS) | 쓰기만 하면 됨 | 제공자 종속 | 경험 적은 팀 |
| 무엇 | 바닐라 | 최신 기능 | 보안 기본값 약함, 튜닝 많음 | 직접 다듬을 역량 |
| 무엇 | 엔터프라이즈 | 보안·사용자 오브젝트·툴 추가 | 업스트림보다 1~2 버전 늦음 | 운영 안정 우선 |

- "쓰는 건 관리하는 것보다 열 배 쉽다" 가 책의 요지
- 매니지드 대표 : GKE, AKS, EKS, OpenShift 등

### 4-1. 애초에 써야 하나

- 큰 모놀리스면 필요 없음
- 마이크로서비스 5개 미만이면 비추, 20개 이상이면 이득. 그 사이는 다른 요인으로 판단
- 개발자도 결국 학습 시간을 씀
- 초기 비용(교육·채용·툴·추가 HW)이 먼저 늘고 장기적으로 줄어듦. K8s 자체도 자원을 먹음

## 5. 사용법 예시

1장은 개념 장이라 실습이 없음. 아래는 흐름을 눈으로 확인하는 최소 예시임

```bash
# 컨트롤 플레인 컴포넌트 확인 (kubeadm·kubespray 계열은 static pod 로 뜸)
kubectl get pods -n kube-system -o wide

# 선언적 배포 : 원하는 상태 적용
kubectl apply -f hello.yaml

# 컨트롤러가 만든 오브젝트 연쇄 확인 : Deployment → ReplicaSet → Pod
kubectl get deploy,rs,pod -l app=hello

# 원하는 상태 변경 → 현재 상태가 따라옴
kubectl scale deploy hello --replicas=3
kubectl get events --sort-by=.lastTimestamp | tail
```

```yaml
# hello.yaml : 2개 복제본 + 단일 IP 서비스
apiVersion: apps/v1
kind: Deployment
metadata:
  name: hello
spec:
  replicas: 2              # 원하는 상태 : 인스턴스 2개
  selector:
    matchLabels: {app: hello}
  template:
    metadata:
      labels: {app: hello}
    spec:
      containers:
      - name: hello
        image: nginx:1.27  # 폐쇄망이면 내부 레지스트리 경로로 교체
        ports:
        - containerPort: 80
---
apiVersion: v1
kind: Service
metadata:
  name: hello
spec:
  selector: {app: hello}   # 이 라벨의 Pod 들로 로드밸런싱
  ports:
  - port: 80
```

## 6. 실무에서 확인

책은 매니지드·개발 클러스터 중심임. 우리처럼 폐쇄망 bare-metal 300+ 노드를 직접 관리하는 쪽에서 보면 다르게 읽히는 부분이 있음

| 책 내용 | 우리 환경에서 |
|---|---|
| 직접 관리는 비추 | 폐쇄망 규제로 매니지드 선택지가 없음. 책이 말한 "어려운 쪽" 을 운영 중 |
| 클라우드는 노드 자동 증설 | bare-metal 은 노드 증설이 구매·랙킹 단위. 오토스케일은 Pod 수준까지만 |
| kube-proxy 가 로드밸런싱 | Cilium kube-proxy replacement 면 eBPF 가 대신함. kube-proxy Pod 가 없을 수 있음 |
| etcd 는 API Server 만 접근 | 1,000명 사용자·네임스페이스 규모면 etcd 크기·컴팩션이 먼저 병목 |
| 노드 100대면 하루 한 대 고장 | 300+ 노드면 확률상 하루 세 대꼴. PDB·여유 자원 확보가 곧 야간 대응량 |
| 셀프서비스 배포 | 사용자별 네임스페이스 + Keycloak 인증 + ArgoCD 로 실현. 단 ResourceQuota 없으면 빽빽한 배치가 독이 됨 |
| 앱은 노드 하나에 들어가야 함 | B300 GPU 분산 학습은 여러 노드 동시 기동이 필요 → Kueue 갱 스케줄링으로 보완 |
| 이미지는 어디서든 받음 | 폐쇄망은 Nexus 미러링 전제. 매니페스트 이미지 경로부터 다름 |

> 주의 : 책 1부는 개발 클러스터 기준이라 컨트롤 플레인 HA·보안·설치는 범위 밖임. 운영 관점은 후속 권에서 다룬다고 함

**이 장의 "관리는 어렵다" 는 경고가 그대로 우리 일상이다. 그래서 컴포넌트 간 watch 구조를 정확히 아는 게 장애 대응의 출발점임**

## 7. 용어 정리

- **선언적 모델(Declarative model)** : 절차 대신 원하는 상태를 기술하는 방식
- **매니페스트(Manifest)** : 오브젝트를 기술한 YAML·JSON 파일
- **오브젝트(Object)** : K8s 에서 모든 것을 표현하는 단위. API 로 생성·조회
- **컨트롤 플레인(Control Plane)** : 클러스터를 제어하는 컴포넌트 묶음
- **워크로드 플레인(Workload Plane)** : 앱이 도는 워커 노드 묶음. 데이터 플레인이라고도 함
- **컨트롤러(Controller)** : 오브젝트를 watch 하다가 실체로 만드는 프로그램
- **스케줄러(Scheduler)** : 인스턴스에 노드를 배정하는 특수 컨트롤러
- **Kubelet** : 노드마다 도는 에이전트. 컨테이너 실행·상태 보고
- **kube-proxy** : 서비스 IP 로 들어온 트래픽을 인스턴스로 분산
- **etcd** : 클러스터 상태를 저장하는 분산 KV 저장소
- **자가 치유(Self-healing)** : 실패한 앱·노드를 자동으로 복구하는 성질
- **KaaS(Kubernetes-as-a-Service)** : 제공자가 관리하는 매니지드 K8s

## 8. 한 장 요약

| 항목 | 핵심 |
|---|---|
| 정체 | 컨테이너 앱 배포·관리 자동화 시스템. 클러스터용 OS |
| 동작 원리 | 원하는 상태 기술 → 컨트롤러가 현재 상태를 맞춤 |
| 구조 | 컨트롤 플레인(API Server·etcd·Scheduler·Controllers) 과 워커(Kubelet·런타임·kube-proxy) |
| 배포 흐름 | API 저장 → 컨트롤러 → 스케줄러 → Kubelet → kube-proxy → 감시 |
| 장점 | 셀프서비스, 활용률, 자동 확장, 자가 치유 |
| 도입 판단 | 어디서 · 누가 관리 · 어떤 배포판. 서비스 20개 이상이면 이득 |

**K8s 는 API 하나를 중심으로 모든 컴포넌트가 watch 하며 원하는 상태를 맞추는 시스템이다**

다음 글 : 2장 컨테이너와 컨테이너화된 앱 이해
